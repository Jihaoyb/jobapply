## 002 Employer identity and dedupe

- **Keys.** An employer-owned application host gives its registrable domain (`careers.acme.example` → `acme.example`; small multi-part suffix list such as `co.uk`). Greenhouse, Lever and Ashby boards give `provider:slug` (including the Greenhouse embed `?for=`). Discovery boards (LinkedIn, Indeed, ZipRecruiter …) and other shared ATS hosts (Workday, Workable …) give no key.
- **Alias table** `employer_aliases(alias_key → employer_id)` is editable from the dashboard (add, reassign, delete; keys are validated). Reassigning or deleting an alias affects future resolution only. Use a merge to combine existing history.
- **Resolution at capture** (`ensureIdentity`):
  - keys mapped to one employer: use it and map the job's unmapped keys to it;
  - keys mapped to different employers: open an `employer_identity` conflict ticket;
  - unmapped keys whose display name or key stem matches an existing employer (for example “Acme Inc.” and `lever:acme-corp`): open a plausible-match ticket, so plausible matches are resolved before applying;
  - no key: a single exact normalized-name match is used, several matches open a ticket, and no match creates a new employer;
  - otherwise create the employer and map its keys.
- **Careers redirect/embed auto-link.** A discovery URL on an employer domain with careers evidence (a careers/jobs path or subdomain, `gh_jid`/`ashby_jid`, or a Greenhouse embed URL) and an application URL on a recognized ATS board link both keys to one employer. Both URLs are recorded in `employer_links` with relation `redirect|embed` and status `linked|conflict|resolved`. When the keys are already mapped to different employers, the job pauses on a conflict ticket. The server never fetches URLs. If the extension later reports observed redirects or iframes, it can send them as the discovery/application pair.
- **Ticket resolution** (`POST /api/identity/tickets/:id/resolve`) takes `{action:'assign'|'merge', employerId}` or `{action:'create', name?}`. It maps unmapped keys, merges if requested, closes the ticket and pause (`pause.closed`, outcome `approved`), restores `resume_status`, then re-runs dedupe/cap/hold and requeues. `create` records the pair as distinct so the suggestion disappears.
- **Merge suggestions** come from normalized display names and key stems and are never merged automatically. `POST /employers/:id/merge` moves aliases, jobs, dedupe keys, submissions and links to the target, so cap and dedupe see one history. When both sides know a requisition, the job with a submission (any state but `not_submitted`) or a non-gateable status stays primary; between equals the older one does (review fix 2). A not-yet-submitted gateable sighting becomes `duplicate` with a `job.duplicate` event and leaves the queue. Merges are flattened (`employers.merged_into`).
- **Domain.** `employers.domain` stays nullable and is exposed in `GET /api/identity/employers` and editable with `PATCH /employers/:id`. A domain key fills it when empty. Shared-ATS-only employers leave it null for issue 010. Domain _confirmation_ for people search remains lane D's step.
- **Dedupe** (`findDuplicate`, per canonical employer). These checks run in order:
  1. Same normalized posting URL means duplicate.
  2. Same requisition ID means duplicate.
  3. Requisition IDs in the same namespace that differ mean distinct positions.
  4. Otherwise, matching normalized title and location keys mean duplicate.

  Requisition IDs are namespaced (`greenhouse:123`, `lever:<uuid>`, `ashby:<uuid>`, `text:R-123` from “Req ID:” text), so only comparable IDs can prove two positions distinct. A partial unique index enforces `(canonical employer, requisition)` among primary records. Title equivalents: Sr./Senior, SWE/Software Engineer, II/2 (and III/3, IV/4, trailing I/1, Jr./Junior), with parentheticals dropped. A location key is `arrangement|city|state|scope`. A US state implies scope `us`. “Remote” (`remote|?|?|?`) ≠ “Remote - US” (`remote|?|?|us`); “Los Angeles, California” = “Los Angeles, CA”. Missing components stay `?`. The location comes from a `Location:` line, a short heading-like line near the top, or a title parenthetical.

- **Order at capture.** Capture runs `job.selected`, then identity, then duplicate linking (`status duplicate` + `job.duplicate {existingJobId}`), then cap (`status capped` + `job.capped {nextAvailableDate}`), then hold, then enqueue. All of this happens before any eligibility work. The hook runs in a savepoint: on failure the capture still commits as `captured` and queued, and the dequeue gate retries identity.

## 003 History import

- `POST /api/identity/imports {filename, csv}` with the header `employer,title,date,source URL` (aliases `source_url`, `url` accepted), ISO local dates, and an http(s) source URL. Per-row errors give line, column and an actionable message (bad/impossible/future date, missing fields, wrong column count, bad URL). Exact repeats inside one file are reported and imported once. Valid rows import even if other rows fail; re-uploading is safe.
- **Representation (tickets.job_id is NOT NULL).** Every counted row becomes a job (`source='manual'`, `status='confirmed'`, explanatory `posting_text`, **no `job.selected`**, so it never enters the pilot funnel) plus a `submissions` row (`kind='imported'`, `state='confirmed'`, `local_date` = the row's date). An unmatched employer creates the job for the first such row and opens an `import_ambiguity`/`resolve_import` ticket on it. Later rows for the same normalized name and key attach to that open ticket (`import_rows.ticket_id`) and get their jobs on resolution. Only `pause.opened/closed` events are emitted for import jobs. Downstream lanes can tell imported jobs apart via `submissions.kind='imported'` or `import_rows.job_id`; they never emit `application.confirmed`.
- **Matching.** An alias match from the source URL key resolves the employer; with no key, a single exact display-name match also resolves it. An unmapped key or an ambiguous or missing name opens a ticket. On resolution the key becomes an alias (source `import`), and the rows count on their **original** local dates.
- **Idempotence.** `import_rows` is unique by a hash of normalized employer, title, date and URL, so re-imports return `already_imported`. A row that matches an existing confirmed or in-flight (`submitting`/`uncertain`) submission for the same employer (same URL, same requisition, or same normalized title within ±1 day with no conflicting requisition) is `linked` to it, keeping one submission. An imported row also turns a queued, unsubmitted sighting of the same URL or requisition into its duplicate.

## 004 Queue, cap and holds

- **Cap math (pure, `capdates.ts`).** Dates are LA calendar dates (`Intl` with `America/Los_Angeles`), so DST never shifts a window. The window is `(subtractMonthsClamped(today, N), today]`, clamped to the last valid day. Settings default to limit 3 and N 3, editable per applicant (`cap_settings`, `PUT /api/identity/cap-settings`). Only `confirmed` submissions count, live or imported. The next available date is the first day on which the window count falls below the limit.
- **Holds.** A `submitting` or `uncertain` submission for the employer holds every other job of that employer. Held jobs stay queued with `hold_reason` and are skipped.
- **Queue** (`work_queue`, one `active` row per applicant via a partial unique index). Capture enqueues. `dequeueNext` re-resolves the canonical employer, rechecks duplicate, cap and hold, and only then activates. It resumes an existing active job after the same recheck (worker restart). A job left `submitting` by a dead session becomes `uncertain` (`application.uncertain`), and its employer stays held. `pauseActive` and `completeActive` free the tab; `resumeQueued` returns a job after its ticket is resolved (the full recheck repeats on dequeue).
- **Lane B hook.** `gateBeforeEligibility(db, applicantId, jobId)` returns `{allowed, result}`. Lane B should call it immediately before eligibility routing or any model call; the queue already calls it on dequeue. No lane B code is imported.
- **Atomic pre-submit.** `beginSubmit` takes the applicant advisory lock plus the employer row lock (`FOR UPDATE`), requires the job to be the active item, rechecks duplicate, cap and hold, and in the same transaction inserts the `submitting` submission (local date), sets job `submitting` and emits `application.submitting`. A refusal (`capped`/`held`/…) means the final click must not happen. `confirmSubmission(receiptId)` makes it count. `markUncertain` and `reconcileSubmission({outcome:'confirmed',receiptId}|{outcome:'not_submitted'})` cover the uncertain path; `not_submitted` releases the hold and requeues the job as `ready`.
- **Display.** `GET /api/identity/queue` shows each item's state, hold reason, and the next eligible date when its employer is capped. `GET /api/identity/employers` shows count/limit, window start, next available date and holds. A capped job can be requeued (`POST /api/identity/jobs/:id/requeue`) and is gated again.

## For human review

- `ledger.captureJob` now returns the job _after_ identity: `status` may be `duplicate`, `capped` or `paused` (identity ticket), and `canonicalEmployerId` is filled. P1 tests are unchanged and pass.
- `tickets.ts` duplicates the SQL of `ledger.openTicket` and the close half of `resolveTicket`, so ticket and pause commit atomically inside identity/import transactions. If other lanes need the same, consider extracting `openTicketTx`/`closeTicketTx` into `ledger.ts` at merge time.
- Heuristics to sanity-check: careers-page evidence (a path or subdomain token, or an ATS job parameter); the no-key exact-name auto-assign; ±1-day title matching on import; “Remote - CA” is read as California (a 2-letter state code); scope only covers a small country/region list.
- Fixtures are synthetic: fictional employers on `*.example` domains or fictional ATS slugs, with no real people.
